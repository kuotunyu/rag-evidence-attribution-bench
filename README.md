# rag-evidence-attribution-bench

Which context passages does a RAG answer *actually* depend on?

A benchmark on **HotpotQA (distractor)** comparing evidence-attribution methods for
**Qwen/Qwen3-4B-Instruct-2507** answers — attribution quality vs. supporting-fact ground
truth, faithfulness (sufficiency / comprehensiveness), latency, and peak VRAM — with
controls, locked splits, content fingerprints, and a no-fabrication results pipeline.

> 繁體中文說明請見 [README_zh-TW.md](README_zh-TW.md).

## What's in the benchmark

- **Data**: 320 HotpotQA-distractor questions in disjoint splits — smoke 20 / dev 60 /
  **locked eval 240** — pinned by per-example SHA-256 fingerprints in a committed
  manifest ([DATA_CARD.md](DATA_CARD.md)).
- **Retrieval**: BM25, dense (Qwen3-Embedding-0.6B), hybrid RRF — per-question ranking of
  the 10 candidate passages.
- **Generation**: deterministic greedy Qwen3-4B with inline `[P#]` citations and explicit
  abstention; checkpointed with `--resume` at per-sample granularity.
- **Attribution** (`attribute(question, passages, target_answer, model, method_config)`):
  `citations`, `embedding`, `leave_one_out` (primary causal baseline), experimental
  `arc_jsd`, optional `contextcite` — plus 5 controls (random / retrieval-rank / lexical /
  length / shuffled) flowing through the identical pipeline ([MODEL_CARD.md](MODEL_CARD.md)).
- **Two evaluation modes, never mixed**: A = teacher-forced gold answers (all samples);
  B = generated answers, with agreement metrics restricted to the correct subset
  (subset sizes always reported).
- **Integrity by construction**: results only enter the repo through real executions or
  sha256-verified `import-results`; mock-backend runs are stamped `execution_kind: mock`
  and structurally excluded from the README; partial runs are excluded from `evaluate`
  unless explicitly `--allow-partial` (and then visibly labeled).

## Results

**Complete.** All three splits were executed end-to-end on real hardware, imported, and
independently re-derived from the raw per-sample records on a second machine (the EM
cross-check passes on every split). Every number below is generated from
`results/derived/summary.json` by `python -m rag_evidence.cli report` — never edited by
hand. Re-deriving from raw is deterministic: it reproduces these numbers bit-identically.

`eval` (n=240) is the locked split and the one to quote. `smoke` (n=20) is a pipeline
sanity check whose accuracy is noisy by construction. Rows tagged `(cpu)` for dense
retrieval are the honest — and expectedly slow — local CPU timings from before the GPU
runs; the `(NVIDIA A100…)` rows are the ones to read for latency.

## Controlled cross-encoder reranking extension

The tables above are the immutable **original evidence-attribution benchmark**. A separate,
preregistered extension asks whether reranking improvements propagate to citation coverage,
evidence sufficiency/comprehensiveness, and answer faithfulness. Its raw/derived artifacts
live under `results/reranking/`, so the extension cannot overwrite the original benchmark.

- Locked design: [PREREGISTRATION_RERANKING.md](PREREGISTRATION_RERANKING.md)
- Locked secondary transfer analysis:
  [SECONDARY_ANALYSIS_RERANKING.md](SECONDARY_ANALYSIS_RERANKING.md). It adds paired
  bootstrap intervals, transfer quadrants, subgroup descriptions, and cold/warm systems
  accounting without changing the primary decision rule.
- New arm: `hybrid_rrf_rerank`, using a replaceable in-repo adapter for
  `BAAI/bge-reranker-v2-m3` at exact model/tokenizer revisions.
- Fair comparison: all four arms use the same query, fixed 10-passage candidate set,
  top-5 context, generator, decoding, attribution methods, metrics, and seeds.
- Top-30/top-50 is inapplicable here because each question has exactly 10 committed
  candidates. Expanding the corpus would be a separate experiment.

## Quickstart (local, CPU)

```bash
uv sync --extra ml --extra app

python -m rag_evidence.cli data prepare --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method bm25       --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method dense      --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method hybrid_rrf --config configs/smoke.yaml
python -m rag_evidence.cli evaluate --config configs/smoke.yaml
python -m rag_evidence.cli report   --config configs/smoke.yaml

# precomputed-results explorer + API on :8000 (no model download, no GPU)
docker compose up            # or: python -m rag_evidence.cli serve --config configs/full.yaml
```

## Reproducing the GPU stages (Google Colab)

The published results were produced this way. The 4B-model stages (generate,
leave_one_out / arc_jsd / contextcite attribution, faithfulness logprobs) run on Colab;
everything downstream is CPU arithmetic:

1. `uv run python scripts/make_colab_bundle.py` → produces `reab_bundle.zip`.
2. Open a notebook in Colab, pick a GPU runtime, and **choose that zip when the upload
   cell prompts** (a native file picker — no Drive folder to create, no path to type):
   - [notebooks/00_colab_smoke.ipynb](notebooks/00_colab_smoke.ipynb) — 20 questions,
     measured ~1.5 h on a T4 (pipeline sanity check).
   - [notebooks/01_colab_run.ipynb](notebooks/01_colab_run.ipynb) — dev 60 + locked
     eval 240, measured ~4.5 h total on an A100. Checkpoints live on Drive, so a
     disconnect resumes with Runtime → Run all.
3. Each section downloads its own export zip. Back on the local machine:
   `python -m rag_evidence.cli import-results <zip> --config <cfg>` → `evaluate` →
   `report` regenerates every table in this README from the raw records.

**Running the GPU stages locally instead of on Colab** (e.g. on a CUDA workstation):
see [TRANSFER.md](TRANSFER.md) — the committed lock deliberately pins Windows torch to
the **CPU** build, so a CUDA machine needs one documented opt-in step.

## CLI

```
python -m rag_evidence.cli data prepare   --config <cfg>
python -m rag_evidence.cli retrieve       --method bm25|dense|hybrid_rrf|hybrid_rrf_rerank --config <cfg> [--resume]
python -m rag_evidence.cli generate       --config <cfg> [--resume]
python -m rag_evidence.cli attribute      --method citations|embedding|leave_one_out|arc_jsd|contextcite|control_* --config <cfg> [--mode gold|generated] [--resume]
python -m rag_evidence.cli evaluate       --config <cfg> [--allow-partial]
python -m rag_evidence.cli report         --config <cfg>
python -m rag_evidence.cli serve          --config <cfg>
python -m rag_evidence.cli status|export  --config <cfg>
python -m rag_evidence.cli import-results <zip> --config <cfg>
python -m rag_evidence.cli reranking generate  --arm bm25|dense|hybrid_rrf|hybrid_rrf_rerank --config <cfg> [--resume]
python -m rag_evidence.cli reranking attribute --arm <arm> --method <method> --config <cfg> [--resume]
python -m rag_evidence.cli reranking evaluate  --config <cfg>
python -m rag_evidence.cli reranking report    --config <cfg>
```

API: `GET /health`, `GET /methods`, `GET /benchmark/{sample_id}`, `POST /retrieve`,
`POST /answer`, `POST /attribute` (precomputed mode; Gradio explorer mounted at `/app`).

```

                      evaluation, reporting, storage, api/explorer)

```
