# rag-evidence-attribution-bench

RAG 的回答，到底真正依賴哪些 context passages？

本專案是以 **HotpotQA (distractor)** 為基礎的 benchmark，比較多種 evidence attribution
方法對 **Qwen/Qwen3-4B-Instruct-2507** 回答的歸因品質（對照 supporting facts）、
faithfulness（sufficiency / comprehensiveness）、latency 與 peak VRAM——含 controls、
鎖定 split、內容 fingerprint，以及「不可捏造結果」的 pipeline 設計。

> English version: [README_en.md](README_en.md)

## Benchmark 內容

- **資料**：320 題 HotpotQA-distractor，互斥 splits——smoke 20 / dev 60 /
  **鎖定 eval 240**，以 committed manifest 的 per-example SHA-256 fingerprint 固定
  （[DATA_CARD.md](DATA_CARD.md)）。
- **Retrieval**：BM25、dense（Qwen3-Embedding-0.6B）、hybrid RRF——對每題的 10 個候選
  passages 排序。
- **Generation**：deterministic greedy Qwen3-4B，行內 `[P#]` citations 與明確 abstain；
  per-sample checkpoint + `--resume`。
- **Attribution**（`attribute(question, passages, target_answer, model, method_config)`）：
  `citations`、`embedding`、`leave_one_out`（主要 causal baseline）、實驗性 `arc_jsd`、
  選配 `contextcite`，加上 5 個 controls（random / retrieval-rank / lexical / length /
  shuffled），全部走同一條 pipeline（[MODEL_CARD.md](MODEL_CARD.md)）。
- **兩種評測模式，永不混用**：A = teacher-forced gold answers（全部樣本）；
  B = generated answers，agreement metrics 只在答對子集上聚合（子集大小必回報）。
- **結構性誠實**：結果只能經由真實執行或 sha256 驗證的 `import-results` 進入 repo；
  mock backend 的 run 標記 `execution_kind: mock`，結構上不可能進 README；未完成的
  run 除非 `--allow-partial`（且明顯標示）否則不納入 evaluate。

## 結果

**已完成。** 三個 split 全部在真實硬體上跑完、匯入，並在另一台機器上從 raw 逐題紀錄

`python -m rag_evidence.cli report` 從 `results/derived/summary.json` 產生，絕不手動編輯。
從 raw 重新推導是確定性的：會逐位元重現同樣的數字。

其準確率本質上就有很大雜訊。dense retrieval 標示 `(cpu)` 的列是 GPU 執行前的本機 CPU
計時（誠實但本來就慢），要看 latency 請看 `(NVIDIA A100…)` 那幾列。

## 嚴格控制的 cross-encoder reranking 延伸實驗

上方表格是不可覆寫的**原始 Evidence Attribution benchmark**。新的預註冊延伸實驗
獨立回答：reranking 對 retrieval 的改善，是否會傳遞到 citation coverage、
evidence sufficiency/comprehensiveness 與答案 faithfulness。所有新 artifacts 都寫入
`results/reranking/`，不會覆蓋原研究結果。

- 鎖定設計：[PREREGISTRATION_RERANKING.md](PREREGISTRATION_RERANKING.md)
- 鎖定的 secondary transfer analysis：
  [SECONDARY_ANALYSIS_RERANKING.md](SECONDARY_ANALYSIS_RERANKING.md)。它新增 paired
  bootstrap、transfer 四象限、題型分層與 cold/warm systems accounting，但不改動
  primary decision rule。
- 新方法：`hybrid_rrf_rerank`，透過 repo 內可替換 adapter 使用固定 revision 的
  `BAAI/bge-reranker-v2-m3`。
- 公平比較：四個 arms 使用相同 query、每題固定 10 個 candidates、top-5 context、
  generator、decoding、attribution methods、metrics 與 seeds。
- 本 benchmark 每題只有 10 個 committed candidates，因此 top-30/top-50 不具
  實質意義；擴大 corpus 必須另立實驗。

## 快速開始（本機，CPU）

```bash
uv sync --extra ml --extra app

python -m rag_evidence.cli data prepare --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method bm25       --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method dense      --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method hybrid_rrf --config configs/smoke.yaml
python -m rag_evidence.cli evaluate --config configs/smoke.yaml
python -m rag_evidence.cli report   --config configs/smoke.yaml

# 預計算結果 explorer + API（:8000，不下載模型、不需 GPU）
docker compose up            # 或 python -m rag_evidence.cli serve --config configs/full.yaml
```

## 重現 GPU 階段（Google Colab）

已發布的結果就是這樣產生的。需要 4B 模型的階段（generate、leave_one_out / arc_jsd /
contextcite attribution、faithfulness logprobs）在 Colab 執行；之後全是 CPU 計算：

1. `uv run python scripts/make_colab_bundle.py` → 產生 `reab_bundle.zip`。
2. 在 Colab 開啟 notebook、選 GPU 執行階段，**在上傳格跳出時選擇該 zip**（原生檔案
   選擇器——不需建立 Drive 資料夾、不需輸入路徑）：
   - [notebooks/00_colab_smoke.ipynb](notebooks/00_colab_smoke.ipynb) — 20 題，
     T4 實測約 1.5 小時（pipeline 健檢）。
   - [notebooks/01_colab_run.ipynb](notebooks/01_colab_run.ipynb) — dev 60 + 鎖定
     eval 240，A100 實測合計約 4.5 小時。Checkpoints 存在 Drive，斷線後
     Runtime → Run all 即可續跑。
3. 每個區段各自下載自己的 export zip。回到本機：
   `python -m rag_evidence.cli import-results <zip> --config <cfg>` → `evaluate` →
   `report`，即可從 raw 紀錄重新產生 README 中所有表格。

**想在本機 GPU（而非 Colab）跑 GPU 階段**：請見 [TRANSFER.md](TRANSFER.md)——
committed 的 lock 刻意把 Windows 的 torch 指向 **CPU** build，CUDA 機器需要一個
明確的 opt-in 步驟。

## CLI

```
python -m rag_evidence.cli data prepare   --config <cfg>
python -m rag_evidence.cli retrieve       --method bm25|dense|hybrid_rrf|hybrid_rrf_rerank --config <cfg> [--resume]
python -m rag_evidence.cli generate       --config <cfg> [--resume]
python -m rag_evidence.cli attribute      --method citations|embedding|leave_one_out|arc_jsd|contextcite|control_* --config <cfg> [--mode gold|generated] [--resume]
python -m rag_evidence.cli evaluate       --config <cfg> [--allow-partial]
python -m rag_evidence.cli report         --config <cfg>
python -m rag_evidence.cli serve          --config <cfg>
python -m rag_evidence.cli status|export  --config <cfg>
python -m rag_evidence.cli import-results <zip> --config <cfg>
python -m rag_evidence.cli reranking generate  --arm bm25|dense|hybrid_rrf|hybrid_rrf_rerank --config <cfg> [--resume]
python -m rag_evidence.cli reranking attribute --arm <arm> --method <method> --config <cfg> [--resume]
python -m rag_evidence.cli reranking evaluate  --config <cfg>
python -m rag_evidence.cli reranking report    --config <cfg>
```

`POST /answer`、`POST /attribute`（precomputed 模式；Gradio explorer 掛載於 `/app`）。
