# rag-evidence-attribution-bench

RAG 的回答，到底真正依賴哪些 context passages？

本專案是以 **HotpotQA (distractor)** 為基礎的 benchmark，比較多種 evidence attribution
方法對 **Qwen/Qwen3-4B-Instruct-2507** 回答的歸因品質（對照 supporting facts）、
faithfulness（sufficiency / comprehensiveness）、latency 與 peak VRAM——含 controls、
鎖定 split、內容 fingerprint，以及「不可捏造結果」的 pipeline 設計。

> English version: [README.md](README.md)

## Benchmark 內容

- **資料**：320 題 HotpotQA-distractor，互斥 splits——smoke 20 / dev 60 /
  **鎖定 eval 240**，以 committed manifest 的 per-example SHA-256 fingerprint 固定
  （[DATA_CARD.md](DATA_CARD.md)）。
- **Retrieval**：BM25、dense（Qwen3-Embedding-0.6B）、hybrid RRF——對每題的 10 個候選
  passages 排序。
- **Generation**：deterministic greedy Qwen3-4B，行內 `[P#]` citations 與明確 abstain；
  per-sample checkpoint + `--resume`。
- **Attribution**（`attribute(question, passages, target_answer, model, method_config)`）：
  `citations`、`embedding`、`leave_one_out`（主要 causal baseline）、實驗性 `arc_jsd`、
  選配 `contextcite`，加上 5 個 controls（random / retrieval-rank / lexical / length /
  shuffled），全部走同一條 pipeline（[MODEL_CARD.md](MODEL_CARD.md)）。
- **兩種評測模式，永不混用**：A = teacher-forced gold answers（全部樣本）；
  B = generated answers，agreement metrics 只在答對子集上聚合（子集大小必回報）。
- **結構性誠實**：結果只能經由真實執行或 sha256 驗證的 `import-results` 進入 repo；
  mock backend 的 run 標記 `execution_kind: mock`，結構上不可能進 README；未完成的
  run 除非 `--allow-partial`（且明顯標示）否則不納入 evaluate。

## 快速開始（本機，CPU）

```bash
uv sync --extra ml --extra app

python -m rag_evidence.cli data prepare --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method bm25       --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method dense      --config configs/smoke.yaml
python -m rag_evidence.cli retrieve --method hybrid_rrf --config configs/smoke.yaml
python -m rag_evidence.cli evaluate --config configs/smoke.yaml
python -m rag_evidence.cli report   --config configs/smoke.yaml

# 預計算結果 explorer + API（:8000，不下載模型、不需 GPU）
docker compose up            # 或 python -m rag_evidence.cli serve --config configs/full.yaml
```

## GPU 工作流程（Google Colab）

需要 4B 模型的階段（generate、leave_one_out / arc_jsd / contextcite attribution、
faithfulness logprobs）都在 Colab 執行；之後全是 CPU 計算：

1. `uv run python scripts/make_colab_bundle.py` → 把 `reab_bundle.zip` 上傳到 Drive
   （`MyDrive/reab/`）。
2. 執行 [notebooks/00_colab_smoke.ipynb](notebooks/00_colab_smoke.ipynb)（T4，估計
   25–45 分鐘）。Checkpoints 在 Drive；斷線後 Runtime → Run all 會自動續跑。
3. 下載 export zip，回本機執行：
   `python -m rag_evidence.cli import-results <zip> --config configs/smoke.yaml`
   → `evaluate` → `report`，README 表格就會從 PENDING 變成真實數字。
4. [notebooks/01_colab_run.ipynb](notebooks/01_colab_run.ipynb) 跑 dev 60 + 鎖定
   eval 240（免費 T4 需要跨 session 續跑，這是設計內的正常路徑）。

## CLI

```
python -m rag_evidence.cli data prepare   --config <cfg>
python -m rag_evidence.cli retrieve       --method bm25|dense|hybrid_rrf --config <cfg> [--resume]
python -m rag_evidence.cli generate       --config <cfg> [--resume]
python -m rag_evidence.cli attribute      --method citations|embedding|leave_one_out|arc_jsd|contextcite|control_* --config <cfg> [--mode gold|generated] [--resume]
python -m rag_evidence.cli evaluate       --config <cfg> [--allow-partial]
python -m rag_evidence.cli report         --config <cfg>
python -m rag_evidence.cli serve          --config <cfg>
python -m rag_evidence.cli status|export  --config <cfg>
python -m rag_evidence.cli import-results <zip> --config <cfg>
```

API：`GET /health`、`GET /methods`、`GET /benchmark/{sample_id}`、`POST /retrieve`、
`POST /answer`、`POST /attribute`（precomputed 模式；Gradio explorer 掛載於 `/app`）。
